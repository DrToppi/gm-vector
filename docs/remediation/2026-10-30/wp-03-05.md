# WP-03 and WP-05: bounded plans and verification matrix

Status: **PROPOSED — NOT IMPLEMENTED OR VERIFIED**. This document describes future
checks; it does not report their execution. The programme order remains
**WP-01 → WP-02 → WP-04 → WP-03 → WP-05**. Use the approved final results of
WP-01, WP-02 and WP-04 as the behavioural baseline for WP-03, not the earlier
implementation with known defects. See [programme](README.md),
[other work packages](work-packages.md), [decisions](decisions.md) and
[evidence protocol](evidence.md).

## WP-03 — frontend and technical debt (P2)

### Baseline and bounded scope

At baseline `ab4abfee0bc6b8d16a6453fe3bae1958624af3d9`,
`production/web/package.json` provides build, TypeScript check and localization
checks, but no ESLint, Prettier or component-test command. Existing component
files include `main.tsx`, `Editors.tsx`, `Panels.tsx` and `Chart.tsx`; extraction
must follow responsibilities, not an arbitrary line-count target.

Allowed changes: an approved module map separating API/session coordination,
project/task state transitions, pure date/effort/chart transformations and
presentation; narrow adapters preserving public behaviour; ESLint and Prettier
configuration; component-test infrastructure and critical scenarios; required CI
commands. Record moved symbols and changed import boundaries per commit.

Excluded: replacing React or the build system, broad visual redesign, altering
server calculation or authorization contracts, adding a new global state library
without a decision, deleting existing E2E coverage, unrelated dependency upgrades,
and formatting generated files or backend code. Separate mechanical formatting
from semantic refactoring so reviewers can distinguish them.

Accepted direction: D07 A (Vitest/React Testing Library with ESLint/Prettier) and
D08 A (focused hooks/pure helpers/views in the existing tree). See the
[checked choices](wp-03-decisions.md). Exact dependency versions, rule/ignore
inventory, symbol-level boundaries and the bounded verification plan are frozen
after WP-04 acceptance; no WP-03 code starts during the current package.

### Invariants

- API shapes, request ordering, optimistic revision handling and session isolation
  established by earlier WPs remain unchanged.
- Editors preserve unsaved fields, validation messages and focus across permitted
  refreshes. Cancellation never persists an edit.
- All seven locales retain key parity and user-generated content stays untranslated.
- Gantt and map gestures preserve dates, dependencies, selection, collapse state
  and viewport semantics established by regression fixtures.
- Components do not bypass permission checks, render secret diagnostics or start
  hidden network operations. UI gating supplements, never replaces, server checks.
- Component tests assert observable behaviour with realistic boundaries; a mocked
  API returning success cannot establish server security or scheduling correctness.

## WP-05 — security and operational readiness (P2)

### Baseline and bounded scope

The baseline workflow `.github/workflows/production.yml` runs a required Trivy
HIGH/CRITICAL gate for the proxy image only. It builds application and PostgreSQL
images, but does not apply the same gate to them. `production/scripts/scan-images.py`
can scan all three images and generate inventories; its existence is not evidence
that all-image scanning is mandatory in CI. Browser E2E currently uses Chromium/CDP.

Allowed changes: mandatory scanning of the exact application, proxy and PostgreSQL
release images; evidence/SBOM handling; migration and encrypted backup/restore
fixtures; cross-browser harness and necessary compatibility fixes; authorization,
privacy and deployment regression coverage. Fixes discovered by these checks must
be scoped and reviewed; a finding does not authorize unrelated feature development.

Excluded: changing the licensing model, adding host surveillance or telemetry,
connecting real external directories/mail/calendars, uploading customer backups,
replacing authentication, silently relaxing security gates, and implementing the
separately proposed Git updater. This WP validates upgrade/recovery procedures;
it does not select an automated upgrade architecture.

Pending decisions: blocker severity/reachability and exception policy; supported
upgrade starting versions and recovery objectives; browser harness/version matrix;
required jobs on every PR versus scheduled deeper checks. Final acceptance cannot
claim a mandatory check from a scheduled run against a different SHA or image.

### Invariants

Release scanning is tied to immutable image digests, scanner version and advisory
database timestamp. Scan errors/stale databases are not clean results. Every
blocking finding needs a fix or explicit owner disposition under the approved
policy; implementers cannot self-dismiss it. Image digests actually deployed must
match tested artifacts. Secrets, runtime data and private signing keys stay out
of images, archives, source history and public test artifacts.

A restore is successful only after data and matching encryption/configuration
material are restored and the application works with intended DB privileges.
Database-only row counts cannot establish decryptability or safe restart.
Migration failure leaves a diagnosable state and does not silently launch an old
binary against an incompatible schema. No test sends queued external mail or
calls a real calendar/LDAP endpoint after restore.

The supported upgrade-version list, fixture scale, RTO and RPO are acceptance
inputs requiring approval before implementation. A reasonable test records both
elapsed restore time and the exact timestamp/data boundary recovered; it must not
infer recovery quality from process exit alone.

Acceptance: every mandatory final-SHA/image check completes, no unresolved blocking
finding remains, supported migration paths and application-level recovery are
proven, and the required three-engine matrix passes. Preserve separate outputs
for each engine/image/version path; an aggregate green status is insufficient
without complete membership. Final programme acceptance additionally reruns the
combined WP-01/02/04/03 regressions and independent security review.

Evidence: artifact digests and SBOMs; advisory database timestamps; sanitized scan
reports and exception decisions; before/after schema and data manifests; restore
logs and measured recovery objectives; per-engine test counts, versions and traces;
access matrix; known limitations. Follow [evidence protocol](evidence.md) for
READ-ONLY review and the exact `PASS — INDEPENDENTLY VERIFIED` closing rule.
